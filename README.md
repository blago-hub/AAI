## 🛠 Методология и модели жизненного цикла

### 1. Модель Киневин (Cynefin)
Проект относится к **сложному домену** (по классификации Дэйва Сноудена):
| Фактор | Характеристика | Влияние на домен |
| --- | --- | --- |
| **Команда** | 5 человек, студенты | Малая, но с разным опытом |
| **Требования** | Интерфейс + предметная логика | Требуют анализа, но известны |
| **Технологии** | Веб-приложение, стандартный стек | Причинно-следственные связи понятны после анализа |
| **Заказчик** | Другая команда, доступна на парах | Обратная связь регулярная |
| **Критичность** | Учебный проект | Низкая |

**Направление действий:** Классический проект с элементами Agile. Планируем структуру (ИСР, оценки, расписание), но оставляем место для итеративной проверки гипотез (например, «работает ли чат-формат для повторения вопросов»).

### 2. Agile Suitability Model
| Критерий | Оценка | Комментарий |
| --- | --- | --- |
| Размер команды | ✅ Подходит | 5 человек — оптимально |
| Доступ к заказчику | ✅ Подходит | Заказчик на парах, обратная связь регулярно |
| Вероятность изменений | ⚠️ Средняя | Требования могут меняться, но не хаотично |
| Критичность продукта | ✅ Подходит | Учебный проект, ошибки не критичны |
| Инкрементальная поставка | ✅ Подходит | Можно показывать части (каталог → чат → статистика) |

### 3. Итоговый подход: Гибридная методология
- **Предиктивная часть:** Устав, ИСР, оценки, расписание — для контроля сроков и реализуемости (жёсткий дедлайн семестра, 4 итерации по 2 недели).
- **Адаптивная часть:** Story map, бэклог, итерации по 2 недели, story points, ретроспективы — для гибкости и работы с изменениями.
- **Точка баланса:** Содержание фиксируется на уровне итерации, но может корректироваться между итерациями по согласованию с заказчиком.

## 🎯 Цели проекта (SMART)
- **S (Конкретная):** Веб-приложение с чатом, базой вопросов и статистикой.
- **M (Измеримая):** Минимум 100 вопросов, 2 роли, 1 сквозной сценарий.
- **A (Достижимая):** 4 итерации по 2 недели, команда 5 человек.
- **R (Значимая):** Решает проблему неструктурированной подготовки к собеседованиям.
- **T (Ограниченная во времени):** Сдача до 25.05.2027.

**Уровень реализации продукта:** Рабочий прототип, воспроизводящий основной сценарий: *ментор создаёт набор вопросов → соискатель проходит → ментор видит статистику*. Реальная интеграция с LLM заменяется заглушкой (ответы хранятся в БД).

## 📦 Границы проекта

### ✅ Входит в проект (конкретные поставки):
1. Веб-приложение — доступно по ссылке, работает в браузере.
2. Модуль аутентификации — регистрация/вход для двух ролей.
3. База вопросов — минимум 100 вопросов с категориями (алгоритмы, SQL, системный дизайн).
4. Чат-интерфейс соискателя — прохождение вопросов, получение фидбека (из БД), отслеживание прогресса.
5. Кабинет ментора — создание наборов вопросов, назначение соискателям, просмотр статистики.
6. Демонстрационные данные — заполненная база вопросов и тестовые пользователи.
7. Документация — руководство пользователя (PDF или веб-страница).
8. Приёмочные материалы — чек-лист для заказчика.

### ❌ НЕ входит в проект:
1. Мобильное приложение (iOS/Android).
2. Реальная интеграция с LLM (только заглушка).
3. Оплата, монетизация, подписки.
4. Пост-релизная поддержка и развитие.
5. Обучение сотрудников заказчика.
6. Интеграция с внешними сервисами (hh.ru, LinkedIn и т.п.).

## ✅ Критерии приёмки (Чек-лист)
- [ ] Регистрация и вход работают для обеих ролей.
- [ ] Соискатель видит список доступных наборов вопросов.
- [ ] Соискатель может пройти вопрос и получить фидбек.
- [ ] Прогресс соискателя сохраняется и отображается.
- [ ] Ментор может создать набор вопросов.
- [ ] Ментор может назначить набор соискателю.
- [ ] Ментор видит статистику по соискателю (пройдено/не пройдено).
- [ ] Сквозной сценарий демонстрируется без ошибок.
- [ ] Демонстрационные данные загружены.
- [ ] Документация приложена.

## ⚠️ Ограничения, допущения и риски

### Ограничения:
- 4 итерации по 2 недели.
- Учебный проект, без реального финансирования.
- Заказчик — другая команда, доступна ограниченно.

### Допущения:
- LLM заменяется заглушкой (ответы хранятся в БД) — считается полноценной поставкой.
- Оплата и внешние API имитируются.
- Заказчик не меняет легенду задним числом.

### Высокоуровневые риски:
- 🔄 Изменение требований заказчиком в ходе проекта.
- ⏳ Недооценка трудоёмкости (риск не уложиться в сроки).
- 🖥️ Технические проблемы с хостингом/деплоем.
